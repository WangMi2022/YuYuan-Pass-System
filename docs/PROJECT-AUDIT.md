# YuYuan Pass System 项目审计报告

## 1. 审计说明

- 审计日期：2026-08-13。
- 审计范围：仓库结构、前后端技术栈、业务插件、路由、数据模型、部署脚本、现有文档和 Git 状态。
- 审计方式：静态代码审查、配置核对、脚本和依赖清单检查；运行测试和构建结果以本次提交最终验证记录为准。
- 当前分支：`main`，远程仓库为 `git@github.com:WangMi2022/YuYuan-Pass-System.git`。

## 2. 总体结论

项目已经不是单纯的 Gin-Vue-Admin 示例，而是一套具备明确业务域的企业内部综合管理平台。资产管理是最成熟的核心域，文档协作、发票识别、站点收藏、公告、个人日程、系统外观与后台权限共同构成协同办公能力。

当前工程具备以下交付基础：

- 前后端分离，目录和构建边界清晰。
- 后端使用插件机制承载业务域，新增模块不需要污染系统核心包。
- 认证、Casbin 授权、操作记录和数据库迁移链路完整。
- Docker Compose 部署脚本包含构建、初始化、健康检查和发布验收。
- PostgreSQL、Redis、S3 兼容对象存储采用外部服务，适合企业已有基础设施。
- 业务文档已有基础，本次补齐统一文档中心、架构、接口、功能规格、数据字典和开发指南。

## 3. 技术栈盘点

### 3.1 服务端

| 类别 | 当前实现 |
| --- | --- |
| 语言与运行时 | Go `1.24.0`，toolchain `1.24.2` |
| Web 框架 | Gin `1.10.0` |
| ORM | GORM `1.31.1` |
| 数据库驱动 | PostgreSQL、MySQL、SQL Server、SQLite、Oracle 适配依赖；当前 Compose 方案使用 PostgreSQL |
| 认证与授权 | JWT + Casbin |
| 缓存 | Redis，可配置关闭 |
| 对象存储 | AWS S3 SDK、MinIO/RustFS 兼容接口，以及多种云 OSS 适配 |
| API 文档 | Swaggo / Swagger |
| 日志 | Zap |
| 后台任务 | Cron、发票识别/清理、日程提醒 |

### 3.2 Web 端

| 类别 | 当前实现 |
| --- | --- |
| 框架 | Vue `3.5.x`、Vue Router `4.4.x` |
| 构建工具 | Vite `8.x` |
| UI | Element Plus `2.13.x`、UnoCSS |
| 状态管理 | Pinia `2.2.x` |
| 数据可视化 | ECharts、Vue ECharts、Three.js 动态模块 |
| 文档能力 | Vue Office、Mammoth、Marked、WangEditor、XLSX、x-data-spreadsheet |
| 请求层 | Axios，统一注入 `x-token` 与 `x-user-id` |
| 测试与质量 | Node Test、ESLint、Vite production build |

### 3.3 部署

- `server` 与 `web` 两个应用容器。
- Nginx 监听 `8080`，将 `/api/*` 重写后代理到 `server:8888`。
- PostgreSQL、Redis、RustFS/MinIO 不包含在 Compose 内，由外部基础设施提供。
- `deploy/docker-dev/config.init.yaml` 是当前 Compose 初始化模板，明确使用 `db-type: pgsql`。
- `server/config.docker.yaml` 仍保留上游多数据库示例默认值，不应直接当作当前生产配置。

## 5. 架构优点

1. **业务插件边界明确**：`server/plugin/*` 与 `web/src/plugin/*` 形成相对独立的业务模块。
2. **写操作可审计**：业务写路由普遍挂载 `OperationRecord()`。
3. **权限模型完整**：私有路由统一经过 JWT 和 Casbin，前端菜单与 API 权限可按角色分配。
4. **资产状态变化具备事务性**：业务单提交与资产状态更新、不可变快照写入同一业务流程。
5. **发票金额避免浮点误差**：金额以整数分存储。
6. **文件与业务数据解耦**：对象存储保存原始证据，数据库保存元数据和业务状态。
7. **发布脚本具备门禁意识**：存在构建、健康检查、验收和回滚说明。

## 6. 主要问题与风险

### 6.1 高优先级

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| 示例配置含弱默认 JWT key 和演示地址 | 配置文件被误用于生产时存在安全风险 | 生产只从密钥管理或受控 `.env` 生成配置；启动时拒绝已知弱默认值 |
| Swagger 对业务插件覆盖不完整 | 集成方只能通过代码或前端封装查接口 | 为所有业务插件 API 补齐 Swaggo 注释，并在 CI 检查 Swagger 是否更新 |
| 文档曾滞后于发票和日程功能 | 产品、测试和交付口径不一致 | 将文档更新列入 Definition of Done，本次已建立统一文档体系 |
| 工作区存在与本任务无关的未提交代码 | 发布时容易误提交 | 始终按文件暂存；本次只提交文档文件 |

### 6.2 中优先级

| 问题 | 影响 | 建议 |
| --- | --- | --- |
| Go module 仍使用上游路径 | 品牌和模块身份不一致，未来拆分包时容易混淆 | 在独立版本计划中评估 module rename，不要与业务功能混改 |
| 示例 Docker 配置与当前 PostgreSQL 方案口径不同 | 新维护者可能选错配置 | 在 README 和部署文档明确用途；后续可改名为 `config.example.yaml` |
| 前端插件和普通 view 两套业务落点并存 | 新开发者定位功能需要额外认知 | 在架构文档维护模块映射；长期统一 feature 目录约定 |
| 日程类型配置偏客户端 | 多设备一致性有限 | 若类型成为正式组织配置，应迁移到服务端字典或专表 |
| 部分业务说明依赖页面行为而非自动化契约 | 回归成本偏高 | 为状态机、权限和上传限制补充集成测试 |

### 6.3 低优先级

- 根目录遗留 `PRODUCT.md`、`ASSET-MVP.md`、`READ.md` 等早期说明，内容与正式文档存在部分重叠。
- 插件 README 和注释风格不统一。
- 项目版本号只在 Web 包和 README 中体现，缺少单一版本来源与自动发布说明。

## 7. 改进路线

### P0：安全与发布

1. 启动时校验 JWT、管理员、数据库、Redis、S3 凭据不能使用默认弱值。
2. 在 CI 中执行 Go 测试、前端测试、Lint、Build、`git diff --check` 和敏感信息扫描。
3. 发布以 Git commit 为唯一版本标识，生产保存完整 commit hash。

1. 补齐业务插件 Swagger 注释与示例。

3. 为对象存储失败、数据库成功的跨资源场景建立可恢复任务和监控指标。
